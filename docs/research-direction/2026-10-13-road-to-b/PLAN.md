## Приоритет1: влияет ли выбор представления на полезное сжатие?

Вопрос: одна функция имеет несколько допустимых DoRA представлений. При одном
бюджете сжатия дают ли они существенно разные ошибки/решения? Может ли процедура,
учитывающая эту неоднозначность, лучше сохранять функцию?

Проверяем C_r, который заменяет полный update W−W0 его rank-r SVD approximation,
при той же базе. Сравниваем f(C_r(S_c(theta))) и f(C_r(theta)), предварительно
проверив f(S_c(theta))≈f(theta). Здесь S_c — уже проверенный V/O magnitude gauge.
Полезное следствие — не другая entropy сама по себе, а другой результат
сжатия/распределения бюджета для функционально одинаковых источников.

Ограничение критики: C_r оптимален для Frobenius ошибки конкретной матрицы;
он не обещает оптимальности по функции сети. Класс fixed-base LoRA-r сам не
замкнут относительно произвольной V/O gauge. Различие не доказывает bug SVD
или ошибочность всех методов сжатия. Наш возможный вклад — измерить практическую
цену этого выбора и уменьшить её при явно функциональной цели.

### Дешёвый screen уже сделан

Код: execution/scientific-analysis/screen_compression_gauge.py.
Данные: [compression-witness.json](compression-witness.json).
Два8×8диагональных примера, рациональная арифметика; SVD усечение диагонали
вычисляется точно сортировкой абсолютных диагональных элементов.

- При c=.995/1.005 исходные композиции V/O точно одинаковы.
- В гладком примере расхождение двух сжатых композиций равно .714% нормы
  исходного оператора. В исходном представлении rank1 compression без потери.
- В специально сконструированном примере с близкими ведущими singular values
  то же локальное преобразование даёт35.31% расхождения сжатых операторов.
  Близкий спектральный gap задан намеренно. Это известная чувствительность
  SVD truncation около crossing, а не обнаруженная статистика реальных моделей.
- Простая канонизация положительного первого V элемента к базовому делает
  результаты сжатия точно gauge-invariant, но в гладком примере создаёт28.57%
  ошибки вместо нуля. **Стабильность представления не равна хорошему сжатию.**

Это screen осуществимости и контрпример наивному исправлению, не материал
о качестве LLM. Проценты относятся к нормам линейных операторов, не accuracy.

### Следующий минимальный модельный тест, до Mistral

Готовая Qwen DoRA, CPUFP32 на вычислительном сервере, не локальнойVM.
Сохранённые64train cases использовать только для exploratory development.
Слои0/17/35, V/O, c=.995/1/1.005, целевой rank32, остальные модули фиксированы.
Первый тест локальный по6матрицам; не выдавать его за full-model compression.

Входы и coefficients одинаковы во всех условиях; source revisions и dtype
не меняются. Dense reconstruction control должен пройти перед C_r. Проверить
критерий gauge fidelity, затем измерить KL/RMS/argmax/NLL после C_r, per-module
спектры, E99 ranks и фактический размер представления. E99 — диагностика,
не дополнительный полный прогон. Измерять deployed rank32 factors: один dense
тензор после truncation не доказывает сокращения памяти или времени.

Первичный engineering screen для продолжения: средний RMS расхождения сжатых
выходов при одном из двух заранее заданных c превышает одновременно
(a)10× средний RMS соответствующего несжатого gauge-control и
(b)20% среднего RMS действия исходного C_r. Публиковать оба c и все слои,
не подбирать c/слой по максимальному эффекту. Это gate величины, не p-value.
При вырожденном нулевом denominator сохранить absolute metrics и не делить.

Если проходит, следующий вопрос — **исправление**, а не новая сетка:

1. Baseline: обычный SVD полного delta при исходном представлении.
2. Сильный baseline: activation-aware approximation, с учётом входных активаций;
   его exact objective и существующий источник фиксировать до реализации.
3. Candidate: выбор представления/приближения по сохранению выходов на calibration,
   без обновления исходных A/B/m обучением. Заранее ограничить число вариантов;
   учитывать дополнительные forward passes и размер факторов.
4. Простая canonicalization — отдельный baseline, не объявлять её готовым методом.

Исправление должно сохранять качество исходного случая и снижать ошибку на новых,
не использованных для выбора64train cases при том же параметрическом бюджете.
Выбирать по calibration KL, оценивать на новом наборе KL/NLL и публиковать оба;
голая устойчивость к gauge не считается успехом. Распределять rank по стоимости
r*(in+out), не по сумме рангов матриц разного размера. Не обучать новую модель.
Параметрический выигрыш не выдавать за latency/VRAM gain без реальных измерений.

Stop: если различия сравнимы с численной погрешностью, проявляются лишь при
экстремальном c, или поправка лишь стабилизирует представление и не даёт пользы
против сильного baseline, не раздувать это в новую compression статью.
Сначала4cases/одна пара модулей; затем64/шесть. Защитный timeout CPU4часа,
не ETA; расход измерять, до полной генерации автоматически не расширять.

## Приоритет2: меняется ли научный вывод из-за пути вычислений?

Резервное направление: не «BF16 неточен», а «вывод об относительной важности
компонентов меняется при эквивалентной реализации; контролируемая процедура
исправляет этот вывод». Уже есть отличие эффектов между CPUFP32/CUDABF16,
но одновременно менялись dtype и backend. Уверенная смена знака не показана.

Минимальный тест: CPUFP32 и CPUBF16 на тех же coefficients/входах/attention mode,
затем сопоставить CPUBF16 с уже имеющимся CUDABF16. Это разделяет два сравнения;
не даёт полной factorial precision×backend картины. Аудитировать внутренние
casts и dtype adapter/magnitude, а не только model.dtype. FP32 reference не
объявлять точной математической истиной; moduleFP64 использовать как контроль.

Сравнить original/removeD/official merge и одно фиксированное контрольное
вмешательство в направление. Последнее требует одинаково заданного воздействия
и новой предварительной спецификации; не использовать BF16 calibration как
автоматически точное FP32 energy matching. Результат для статьи — воспроизводимое
изменение значимого заключения о компоненте, подтверждённое на отдельном наборе,
и рабочая процедура измерения через общий численный путь/reference.

Stop: если меняются только logits, а все содержательные контрасты сохраняются,
оставить это validation appendix. Новый стабильный compose kernel не изобретать:
это уже предмет Scaling DoRA. Пороговый no-op residual не выдавать за
математически гарантированную границу любой ошибки абляции.

## Когда нужен Mistral

Реплицировать **успешный практически значимый тест** приоритетов1или2, а не
только ещё раз рост entropy. Состав исходной короткой FP32 репликации сохранён
в docs/analysis/2026-10-13-fidelity-audit/MISTRAL_DECISION.md; сейчас её приоритет
ниже решающего Qwen screen. Выбирать checkpoints заранее, без поиска выигрышных.
Неизвестное происхождение r16/e03 не исчезает; допустим within-checkpoint вывод,
но не чистое сравнение методов обучения. Полный removeD включает gate_proj.

При позитивном screen: независимое семейство плюс дополнительные уже имеющиеся
Qwen task checkpoints (включая случаи без выигрыша DoRA), общий аудит, controls.
Это несколько обученных решений, не много seeds одной процедуры. Новых моделей
не обучать. Полную quality оценку добавлять после фиксирования алгоритма/тезиса
и только когда она способна проверить практическое следствие.

## Что считать материалом с реальной перспективойB

Нужен пакет: чёткая проблема принятия решения → объяснение, когда она возникает →
исправление/валидированный критерий → польза против сильных baselines → независимая
проверка и воспроизводимый код. Новый алгоритм не обязателен, если аудит показывает
серьёзное ранее не установленное последствие и даёт полезную процедуру.
Это критерий выбора работы, не утверждение о правилах любойBконференции.

Сочетание «ещё одна модель + уже известная симметрия + почти прежняя accuracy»
не устраняет главный риск novelty. Если оба приоритета не дают полезного
следствия, честный результат — workshop/ограниченный negative result,
без объявления уровняB и без дальнейшего перебора ради значимости.

## Близкие работы: что уже занято

Проверены13октября2026, первичные источники. Это целевой поиск, не доказательство
отсутствия точного предшественника. Перед заявкой нового алгоритма нужен отдельный
поиск его конкретной формулировки.

| Источник | Уже известное / граница нашей заявки |
|---|---|
| [SORA](https://arxiv.org/html/2511.00051v1) | Entropy полного update предлагается как объяснение DoRA; наши данные ограничивают функциональную интерпретацию, не опровергают training correlation |
| [Transformer gauge symmetries](https://proceedings.mlr.press/v282/wang26a.html) | V/O symmetry известна; нельзя заявить её открытие |
| [TransformerLens OV circuits](https://transformerlensorg.github.io/TransformerLens/generated/demos/Main_Demo.html) | Произведение V/O как функциональный объект известно; переименовать его в новую метрику недостаточно |
| [LoRA-Squeeze](https://arxiv.org/html/2602.10993v2) | Posthoc SVD compression LoRA известна; авторы ограничиваются standard LoRA. DoRA extension требует пользы, одного переноса мало |
| [FermiGrad/PivGa](https://arxiv.org/html/2512.03062v1) | Rank allocation и gauge fixing уже используются в compression; PivGa меняет факторы AB при неизменном произведении, не V/O относительно fixed base |
| [AIR](https://arxiv.org/html/2606.19993v1) | Activation/influence-aware compression — сильный существующий baseline; «учесть активации» не новая идея |
| [Scaling DoRA](https://arxiv.org/html/2603.22276v1) | Near-unity cancellation, stable FP32 compose и fidelity уже разобраны; новый generic precision сюжет слаб |
| [Precision floors in patching](https://www.mdpi.com/2079-3197/14/9/212) | Численная надёжность interpretability measurements уже исследуется; нужна конкретная ценность для PEFT weight interventions |

Дополнительная близкая находка: [Quotient Fréchet model merging](https://openreview.net/pdf?id=FsaM9HE6Cv).
Search metadata указывает gauge alignment LoRA; полный PDF оказался за browser
challenge, поэтому содержание не считаем полностью проверенным и не делаем
приоритетных выводов на его основании. Merging и compression не тождественны.

Один положительный малый screen не делает статьюB. Он решает, оправдана ли
следующая ограниченная проверка, вместо повторения затратной исследовательской сетки.
