# Почему это сравнительный контроль, а не новый метод

Перед реализацией проверена [LoRAQuant v2, §§3.1–3.3](https://arxiv.org/html/2510.26690v2).
Она уже изучает post-training квантизацию самих адаптеров, SVD-перепараметризацию
и разную точность латентных компонент. В опубликованном pipeline есть
straight-through оптимизация; здесь её нет. Наш обычный FP16/INT8 baseline
не объявляется воспроизведением полной LoRAQuant и не имеет самостоятельной
алгоритмической новизны. [Авторский код](https://github.com/Anonymous890920/LoRAQuant)
указан в первоисточнике; в этом этапе не запускался.

Применяем этот известный принцип к структурному `D*W0+LR`, честно учитывая
дополнительные D и scales в байтах. Практическая задача — выяснить, не закрывается
ли весь выигрыш сложного FP32 компрессора более простым способом хранения.
Качество, скорость и занимаемая память при реальном low-bit runtime — разные
проверки; из нашего декодированного FP32 inference следует только первая
метрика fidelity при заданной стоимости хранения.

Другие рассмотренные идеи не запускаем:

- [GFWSVD v2, §3](https://arxiv.org/html/2505.17974v2) прямо допускает true Fisher
  через pseudo-gradients. Замена gold empirical Fisher выборкой меток из teacher
  уже предусмотрена; сама по себе не новая идея компрессора.
- [EigenLoRAx](https://openaccess.thecvf.com/content/CVPR2025W/TCV/papers/Kaushik_EigenLoRAx_Recycling_Adapters_to_Find_Principal_Subspaces_for_Resource-Efficient_Adaptation_CVPRW_2025_paper.pdf)
  уже исследует shared subspaces готовых LoRA, включая zero-shot compression.
  Прямое совместное PCA наших трёх адаптеров без конкретного отличия не запускаем.
- [Scaling DoRA](https://arxiv.org/abs/2603.22276) уже рассматривает устойчивую
  композицию near-unity magnitude и вычислительную реализацию. Общую проблему
  BF16 или новый compose kernel нельзя присвоить себе.

Это целевой поиск, не гарантия полноты литературы. Сейчас выбран один дешёвый
контроль, который способен изменить решение о дальнейшем поиске алгоритма.
