# Решение о следующем семействе: ограниченный Mistral

12 октября 2026. Решение по результатам [A/B/C](REPORT.md), предложение следующего
этапа; новые модельные прогоны и очереди не запущены.

## Зачем запускать

Qwen не выделил D-специфичную устойчивость: сопоставимое ослабление L также
сохранило близкую среднюю. Ещё одна Q/K локализация этот вопрос не разрешит.
Содержательная следующая проверка — сохранится ли результат на другом семействе
с другой готовой адаптацией или появится граница необходимости D.
Заранее не выбирать пару по величине преимущества DoRA.

Выбранная ранее одна пара: `fzzhang/mistralv1_{lora,dora}_r16_25e5_e03`,
база `mistralai/Mistral-7B-v0.1`, r16/alpha32/dropout0.05.
Скачанные revisions: base `27d67f1b5f57dc0953326b2601d68371d40ea8da`,
LoRA `c140f2dbe97a000151b94ee8d078a02ff980e346`,
DoRA `c4e99622a6e01dda3ef3b1cb4e20cbf938a71c7b`.
Файлы прошли SHA-256 проверки; inference пока не выполнялся.

## Состав и приоритеты

Ядро, полный GSM8K test, одни вопросы и prompts:

1. Исходная DoRA.
2. Та же DoRA с removeD во **всех адаптированных модулях**.
3. Та же DoRA с направляющим контролем matched energy.

Отдельная LoRA — четвёртое контекстное условие, если provenance и бюджет
позволяют. Это осознанная коррекция прежнего минимума LoRA/DoRA/removeD:
новые результаты показывают, что контроль другого компонента важнее для
главного вывода, чем ещё одно межмодельное ранжирование.
Приоритетный contrast — removeD против направляющего контроля; original/removeD
показывает абсолютный эффект. LoRA не входит в причинный внутри-checkpoint контраст.

Перестановочный контроль сейчас не включать: один такой контроль уже не
различил объяснения, направляющий отвечает более сильному вопросу о другом
обученном компоненте. Также не включать SVD/energy99, V/O, локализации и другие
Mistral ranks/epochs. Полный base не нужен; достаточно короткой проверки loader.
WikiText DoRA/removeD — только если основной результат даёт конкретный вопрос
о переносе; нынешняя малая NLL потеря сама по себе не требует новой полной серии.

## Условия допуска и конфигурация

- Сначала короткий численный и временной пилот, BF16 без квантизации, batch=1,
  одинаковый unmerged вычислительный путь. Число GPU определяется фактическим
  размещением; смена dtype ради памяти без контроля недопустима.
- Targets у этой пары включают **gate_proj**, кроме q/k/v/o. Текущий Qwen default
  из четырёх attention projections автоматически переносить нельзя. Проверить
  tensors и охват каждого magnitude; ни один gate модуль не пропустить.
- Использовать авторский GSM8K **5-shot** plain-text протокол, без Qwen chat
  template. Фиксировать revision harness/tokenizer, пять демонстраций и их порядок,
  stop sequences, лимит генерации, контекст и извлечение ответа до полной оценки.
  [Авторский task YAML](https://github.com/pilancilab/spectral_adapter/blob/main/mistral_tune/lm-evaluation-harness/lm_eval/tasks/gsm8k/gsm8k.yaml)
  задаёт train fewshot split, greedy, strict `####` и flexible scorer. Сохранять
  оба; не сравнивать Mistral 5-shot и Qwen 0-shot как чистый эффект архитектуры.
  Не наследовать Qwen обрезание input до 512: сначала проверить длины 5-shot,
  затем выбрать общий контекст без потери демонстраций. Лимит генерации надо
  восстановить из pinned harness, YAML сам его явно не задаёт.
- Сопоставить реальный native removeD output impact на 200 train +32 disjoint
  train-примерах с тем же 5-shot режимом; test не использовать для подбора.
  Прежние Qwen scales не переносить. Численно сравнить FP32 идеальное действие
  с native BF16 и нулевой hook. При расхождении, меняющем смысл вмешательства,
  полную серию не запускать; весь новый precision sweep автоматически не нужен.
- Измерить стоимость на нескольких длинах ответов; учесть калибровку, загрузку,
  shared GPU slowdown и возможные две карты в GPU-часах. Потолок следующего
  блока **20 GPU-ч** сохраняется, это не измеренный ETA. Если ядро не помещается,
  пересмотреть план до постановки, а не превышать потолок по факту.

## Пробел происхождения стал конкретнее

Карточки r16/e03 не устанавливают dataset и training base revision. Более того,
доступный [авторский DoRA train script](https://github.com/pilancilab/spectral_adapter/blob/main/mistral_tune/dora_tune/mistral_tune.py)
сейчас задаёт **r8, alpha16, 2 epochs**, а не выбранные r16/alpha32/3 epochs.
Он показывает GSM8K preprocessing, но не доказывает происхождение именно этих
весов. Это не доказанное несовпадение LoRA/DoRA обучения, а отсутствие нужной
связи. Нельзя объявлять аудит пройденным по совпадению имён.

До чистого сравнения методов нужен подходящий commit/config или подтверждение
автора. Без этого допустима только явно ограниченная проверка внутри сохранённой
DoRA: эффекты removeD и направляющего контроля. Не выдавать её за независимую
репликацию чистого эффекта метода; LoRA остаётся описательным ориентиром.
Доказанная идентичность training seeds между парами не нужна для собственно
вмешательства внутри одних весов, но независимые seeds у нас от этого не появляются.

## Что изменит решение

| Исход | Вывод / остановка |
|---|---|
| Оба вмешательства снова близки к original | Перенос устойчивости этой силы; не доказанная эквивалентность. Дальше всю сетку не расширять |
| removeD явно хуже, а контроль нет или слабее | Граница роли радиального компонента на другой паре; проверить численную причину до механистического заявления |
| removeD лучше сохраняет качество, чем контроль | Семейство-зависимое различие; сопоставить масштаб и протокол, не стирать отрицательный Qwen результат |
| Оба сильно хуже | Другая чувствительность этой адаптации; универсальная избыточность не поддерживается |
| Интервалы широки / precision не проходит | Неопределённость / технический gate, без продолжения перебора ради значимости |

До запуска фиксировать главный contrast, интервал и рабочий допустимый эффект.
Разумный будущий ориентир практической сохранности — 1 п.п.; на 1319 вопросах
он может остаться неразрешимым. Не принимать p>0.05 за прохождение этого условия.
