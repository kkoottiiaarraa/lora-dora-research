# SORA: подтверждённые ошибки экспорта и повторной загрузки

14 октября 2026. В публичном коде ближайшего к нашему исследованию метода
найдены две воспроизводимые технические неисправности. Они ограничивают
возможность использовать этот код как готовый comparator. **Влияние на числа
статьи не установлено; нового результата уровня B это само по себе не даёт.**

Исследование относится к [официальному SORA](https://github.com/MaeChd/SORA/tree/24f62bfe84741e5613ae2e9f387f2e1f9bb64ba8),
commit `24f62bfe84741e5613ae2e9f387f2e1f9bb64ba8`, а не к нашим прежним DoRA-прогонам.
Готовые модели не загружались, обучение не выполнялось, GPU: **0 часов**.

## 1. Формула экспорта пропускает часть эффективного веса

Для PyTorch записи веса `W` обозначим:

```
M = diag(d) W + s B A
K = s_P (D Cᵀ − C Dᵀ)
```

Независимое раскрытие авторского forward даёт эффективный вес `(I+K)M`.
Но `get_delta_weight` возвращает `KM−W`; после добавления этого delta
к базе остаётся только `KM`. Потерян весь член `M`.

В штатной инициализации `B=0`, `C=D`, `d=1` исходный слой работает как база,
а эта формула экспорта даёт **нулевую матрицу**. Это не погрешность округления.

| Фиксированный tiny случай | Forward vs независимая формула | Author export vs forward | Исправленный export vs forward | Author round-trip: ошибка веса |
|---|---:|---:|---:|---:|
| Инициализация | 0 | 1.0000 | 0 | 1.0000 |
| Ненулевые компоненты | 1.17e−16 | .99843 | 1.17e−16 | 1.01940 |

Все ошибки относительные L2/Frobenius; это **не accuracy и не проценты качества
LLM**. Методы автора исполнены без изменения через AST в маленьком harness.
Поле `lora_bias['default']=False` задаётся harness явно; это аудит арифметики
без bias, не успешности всех constructor/lifecycle путей авторского класса.
Повторная загрузка ниже исполняет уже весь авторский класс.

`unmerge` отдельно пересчитывает delta от уже изменённого веса и не восстанавливает
базу. Поэтому одной поправки в export недостаточно для исправления lifecycle.
Контроль с сохранением исходного веса восстанавливает его побитно.

## 2. Обычный loader молча теряет три компонента SORA

Создан и сохранён настоящий PEFT checkpoint маленькой модели: пять тензоров
`A/B/C/D/Diag`. Никакого обучения. Затем он загружен в две одинаковые копии базы.

| Повторная загрузка | Фактический слой | Точно сохранённых тензоров | Ошибка выхода: initialization / ненулевой случай |
|---|---|---:|---:|
| PeftModel.from_pretrained без custom mapping | Обычная LoRA Linear | 2/5 | 0 / .195897 |
| С повторной регистрацией SoraLinear | SoraLinear | 5/5 | 0 / 0 |

**Warnings отсутствовали в обоих случаях.** Начальная проверка выхода проходит
даже у неправильного loader: дополнительные ветви тогда не влияют на функцию.
Проверка ключей и значений тензоров обнаруживает потерю и в этом случае.
Документация [PEFT custom modules](https://huggingface.co/docs/peft/main/developer_guides/custom_models)
прямо требует повторной регистрации mapping; это известное требование API.

Результат сначала получен на установленном PEFT 0.17.1, затем воспроизведён
на **неизменённом авторском PEFT 0.14.1.dev0**. Все 124 Python-файла fork
проверены по Git blob SHA1 из pinned tree. Fork импортирован через отдельный
PYTHONPATH; venv не изменялся. В author-fork конфигурации явно сохранено
`adapter_name=sora`; это имя не включает custom dispatcher автоматически.

Static проверка call sites: `finetune_math.py` регистрирует SoraLinear;
`evaluate_gemma_math.py` — нет. В опубликованном lm-evaluation-harness mapping
восстанавливается для polar/rplora, но не SORA. В просмотренных evaluation
путях нет merge. Следовательно, **ошибку merge нельзя приписать их benchmark
числам**. Для loader есть прямой кодовый риск, однако точные release checkpoints,
execution logs и revision, получившая таблицы статьи, нам недоступны.

## 3. Реализованный scale не даёт ограничения из статьи

Авторский код использует знаменатель `norm(C)+norm(D)+1e−6` и cap 1,
а [статья, Theorem 2](https://arxiv.org/html/2511.00051v2#S3.SS2) задаёт
`epsilon / (2 norm(C) norm(D) + epsilon)`. Это разные процедуры.

Для `C=t e1`, `D=t e2`, initial scale 1: спектральная норма `K` в коде
растёт примерно как `t/2`. У `P=I+K` точно `PᵀP−I=KᵀK`.
При `t=1` максимальное растяжение равно 1.1180, при `t=10` — 5.0990;
для формулы статьи с epsilon .01 оно в обоих случаях меньше 1.000013.
Значит, code rule **не обеспечивает равномерную near-orthogonality гарантию**.
Это допустимый синтетический пример, а не измерение обученных SORA факторов.
Точно ортогональные exponential/Cayley/Householder варианты давно известны;
их простая подстановка не заявляется новым алгоритмом.

## Решение для исследования

SORA не включаем как готовый comparator через опубликованный loader без
полной tensor coverage и проверки функции. Наши прежние DoRA-проверки имели
собственные tensor/merge controls; этот аудит их автоматически не отменяет.
Нельзя заявлять опровержение преимущества SORA, DoRA или механизма обучения.

В проверенном tree нет модельных весов, GitHub releases пусты, README не даёт
ссылки на weights. HF поиск по handle MaeChd пуст; соответствие аккаунтов
не доказано. Отсутствие публичных весов где-либо не установлено.
Авторам не писали. Без готовых checkpoints не запускать training или дорогую
псевдорепликацию. Дальнейшая проверка accuracy требует дополнительных артефактов.

Это конкретный результат аудита воспроизводимости. Вклад в статью пока
вспомогательный: исправление известного API misuse и ошибки algebra export
не заменяет новый полезный compression/ablation результат.
